# Putting TLS in front of Orchicon

The plane speaks **plain HTTP**. It does not terminate TLS itself, and it has no
certificate of its own. That is a deliberate boundary, not an omission: the plane
is designed to sit on a host with its internal services, and encryption is the
job of whatever faces the network.

This document is the supported way to expose Orchicon to other machines —
another box on the LAN, or the public internet — **without credentials crossing
the wire in cleartext**.

---

## Read this first: what is and is not protected

By default the plane binds a **wildcard** (`0.0.0.0:<port>`), which is what
makes it reachable from other machines at all. The consequence is blunt and you
should know it before deciding anything else:

> **Direct access to the plane's port is plain HTTP.**
> If a client can reach `http://<host>:8091`, that client's password, bearer
> tokens and refresh cookie are readable by anyone who can observe the traffic.

A reverse proxy fixes this **only if the plane's port is not independently
reachable**. That is the whole point of the setup below: the proxy is the front
door, and the plane's own port is closed at the firewall.

Two things changed to make this work correctly:

- The refresh cookie's `Secure` flag now follows the **actual transport**
  (`r.TLS`, or `X-Forwarded-Proto: https`), not the deployment mode. Previously
  a proxied HTTPS site still received a non-`Secure` cookie, which is a
  downgrade hole. See `internal/auth/handlers.go`.
- Internal services (Postgres, NATS, Tempo, Loki, VictoriaMetrics, the OTel
  collector) are **loopback-only**. They never need to be proxied, and they must
  not be exposed. If you find one listening on `0.0.0.0`, that is a bug — see
  *Checking your own host* below.

> **This was not always true, and the gap was not theoretical.** Tempo's OTLP
> receivers, the collector's OTLP receivers, its health endpoint and its
> self-metrics exporter were all bound to `0.0.0.0`, as was VictoriaMetrics'
> `-httpListenAddr`. On a stock install that put the telemetry pipeline and an
> unauthenticated metrics store on every interface. All of them are loopback
> now.

### What stays plaintext, and why that is fine

| Leg | Transport | Leaves the host? |
|---|---|---|
| Postgres / NATS / telemetry | loopback | never |
| Plane → internal services | loopback | never |
| Proxy → plane | loopback | never |
| Desktop app → plane | loopback (via its own proxy) | never |
| TUI / `orch` CLI → plane | loopback | never |
| **Remote browser → proxy** | **TLS** | **encrypted** |

Cleartext exists only inside the machine, on interfaces that cannot be reached
from off-box.

## Caddy (recommended)

Caddy is the shortest path because it obtains and renews certificates by itself
and needs no separate certbot plumbing.

### LAN-only, with a locally-trusted certificate

For `https://orchicon.lan` (or any internal name) you want Caddy's **local CA**,
not a public certificate. Caddy generates a root CA and issues from it; you
install that root once per client machine.

`/etc/caddy/Caddyfile`:

```caddyfile
{
	# Internal names are issued from Caddy's local CA instead of Let's Encrypt.
	local_certs
}

# One hostname per instance. Caddy routes by NAME, so dev/prod/test can all be
# served from one listener on 443 with no port juggling.
orchicon.lan {
	reverse_proxy 127.0.0.1:8091 {
		# THE PLANE STREAMS. Execution output arrives as a long-lived response;
		# with buffering on, the UI appears frozen while work is happening.
		# These two lines are not tuning — they are required for streaming.
		flush_interval -1
	}
}

# A second instance on the same host:
# orchicon-dev.lan {
# 	reverse_proxy 127.0.0.1:8080
# }
```

Then:

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy

# Install Caddy's local root CA into THIS machine's trust store. Repeat on each
# client machine that needs to trust the certificate — this is per-client and
# cannot be done from the server.
caddy trust
```

Point `orchicon.lan` at the host in your DNS or `/etc/hosts` (or use mDNS).

> **Why not a self-signed cert generated by Orchicon?** Because a certificate is
> only useful if the client already trusts its issuer, and no server can install
> a trust anchor into a remote client's store. Caddy's local CA solves exactly
> that, with one `caddy trust` per machine. A cert the plane minted for itself
> would give every browser an interstitial that cannot be permanently dismissed.

### Public internet, with a real certificate

Same file, drop `local_certs`, and use a real hostname that resolves publicly:

```caddyfile
orchicon.example.com {
	reverse_proxy 127.0.0.1:8091 {
		flush_interval -1
	}
}
```

Caddy gets a Let's Encrypt certificate automatically. Requirements:

- ports **80 and 443** reachable from the internet (80 is needed for the ACME
  HTTP challenge; 443 serves traffic),
- a DNS record for the hostname pointing at your public address.

Caddy needs to bind `:443`, which requires privilege. Either run it under a
systemd unit as root (Caddy drops privileges itself afterwards), or grant the
capability once:

```bash
sudo setcap cap_net_bind_service=+ep "$(command -v caddy)"
```

### Then close the plane's own port

**This is the step that makes the encryption mean anything.** If `8091` stays
reachable, the plaintext path bypasses the proxy entirely.

```bash
# Deny direct access to the plane, allowing only loopback (the proxy).
sudo ufw deny 8091/tcp
sudo ufw reload

# Verify: this must FAIL from another machine.
#   curl -m 3 http://<host>:8091/healthz
```

`ufw deny` on a port that a local process serves does not affect loopback
traffic, so the proxy and local clients keep working.

## nginx (if you already run it)

```nginx
server {
    listen 443 ssl;
    http2 on;
    server_name orchicon.example.com;

    ssl_certificate     /etc/letsencrypt/live/orchicon.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/orchicon.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8091;

        # Preserve the public Host. The embedded OIDC provider derives its
        # issuer from the request Host, so a rewritten Host makes the issuer
        # disagree with what the browser sees and breaks login.
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # REQUIRED FOR STREAMING. Execution output is a long-lived response;
        # with buffering on, the UI looks frozen while work is running.
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;

        # Connect RPC over HTTP/1.1 uses chunked streaming.
        proxy_http_version 1.1;
    }
}
```

## Login will not work until the OIDC origin matches

The plane embeds an OIDC provider. It has to agree with the browser about the
origin, or the redirect is rejected after a successful password entry.

Set these in the plane's environment:

```bash
# The origin the BROWSER sees — scheme included.
ORCHICON_OIDC_REDIRECT_URL=https://orchicon.example.com/auth/callback
ORCHICON_OP_REDIRECT_URIS=https://orchicon.example.com/auth/callback

# Pin the issuer instead of deriving it from the request Host. A derived issuer
# can flap between http:// and https:// depending on how the proxy forwards,
# and a flapping issuer invalidates tokens mid-session.
ORCHICON_OP_ISSUER=https://orchicon.example.com
```

`ORCHICON_OIDC_REDIRECT_URL` defaults to `http://localhost:5173/auth/callback`,
which is the Vite dev server. Leaving it at the default is why a proxied setup
often completes the password step and then fails at the callback.

> **Known limitation.** These three values are read by the plane process, but the
> host launchers currently pass a fixed set of variables through to it. Until
> that pass-through is widened, setting them in your shell does not reach a
> plane started by `orchicon install`. Track this separately from the proxy
> setup.

## Verifying it actually works

Run these in order; each one isolates a different layer.

```bash
# 1. The plane is healthy locally.
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8091/healthz   # 200

# 2. The plane is NOT reachable directly from off-box (from another machine):
curl -m 3 http://<host>:8091/healthz                                     # must fail

# 3. TLS works through the proxy (from another machine):
curl -sS -o /dev/null -w '%{http_code}\n' https://orchicon.lan/healthz    # 200

# 4. The cookie is Secure over HTTPS. This is the one that proves credentials
#    are not downgraded — look for "Secure" in the Set-Cookie line.
curl -sS -i -X POST https://orchicon.lan/orchicon.api.v1.AuthService/Login \
  -H 'Content-Type: application/json' -d '{"username":"...","password":"..."}' \
  | grep -i set-cookie
```

If step 4 shows a `Set-Cookie` **without** `Secure`, `X-Forwarded-Proto` is not
reaching the plane — check the `proxy_set_header` line.

## Checking your own host

Run this on the Orchicon host. Every listener should name `127.0.0.1` (or the
plane's own port, which is intentionally wildcard):

```bash
ss -ltn | awk 'NR==1 || $4 ~ /^(0\.0\.0\.0|\*):/'
```

The **only** entry you should see is the plane itself on its control port. If
Postgres, NATS, Tempo, Loki, VictoriaMetrics or the OTel collector appear here,
they are reachable from the network and should not be.

## Troubleshooting

**Browser shows a certificate warning.** The client has not trusted Caddy's
local CA. Run `caddy trust` on that machine (not the server).

**Login redirects, then fails.** `ORCHICON_OIDC_REDIRECT_URL` /
`ORCHICON_OP_REDIRECT_URIS` do not match the origin in the address bar exactly —
scheme included.

**The UI freezes during a run.** Response buffering is on. `flush_interval -1`
(Caddy) or `proxy_buffering off` (nginx).

**`curl` to the plane port still works from another machine.** The firewall rule
did not take, or the plane is bound to a different port than you think. Confirm
with `ss -ltn 'sport = :8091'` on the host.

**Works over IP but not hostname.** The certificate's SANs cover the hostname,
not the IP (or vice versa). Add the name you actually type to the site block.
