# ADR-0007: Session engine — agent loop, transcript & resume

Status: **Proposed** (architect design, workflow step 1)
Work item: "Session engine: agent loop, transcript & resume"
Full design + test plan: `architecture-notes/session-engine-agent-loop-transcript-resume.md` (worker artifact of the architect step).

## Context

The native adapter is the in-process replacement for the opencode session bridge: the control plane itself runs the agent turn loop against the provider layer (`internal/orchicon` wire clients, ADR-0003) and exposes the worker session through the `scheduler.AdapterBridge` contract so the Dispatcher treats it like any other adapter. The provider substrate (PR #459) and the adapter namespace/dispatcher (PR #455) are landed; what does not exist is the session engine itself: the loop that streams turns, executes tools, persists a crash-safe transcript, supports mid-run message injection, cancellation, resume, turn-loop guards, and panic containment. The durable execution transcript today is the DB `execution_session_parts` table (kind+payload jsonb, RLS, idempotent append) written by the opencode adapter; it is reconciliation-visible but not crash-safe per-event (batched flush), so a kill -9 can lose the trailing batch. The engine needs a crash-safe source of truth for replay/resume fidelity while keeping the DB parts as the reconciliation-visible record.

Design constraints verified in-repo: `AdapterBridge` = `Start` only, plus optional capabilities (`MessageInjector`/`Aborter`/`LivenessReporter`/`SessionContinuer`/`ConfigurableBridge`); the Dispatcher resolves bridges by `adapter.AdapterKind(model_ref)` with the concrete type appearing only at server construction; the provider layer is a leaf (`go list -deps` shows no scheduler/adapter/worker import), so a bridge package importing `scheduler` introduces no cycle; `Provider.StreamTurn` emits normalized events (`TextDelta`/`ReasoningDelta`/`ToolCallStart|Delta|End`/`ToolCall`/`StreamError`/`Finish{StopReason,Usage}`) and never replays reasoning into history; `db.StablePromptPrefix` is the byte-identical shared prompt prefix that the prompt-assembly task uses as the provider cache breakpoint; opencode parity surfaces are OnStarted/OnText (chunked; reasoning via a `{"kind":"reasoning"}` JSON wrapper)/OnToolCall/OnWrittenFiles/OnArtifact/OnResult, completion on session idle, and stall reasons `stalled:no_progress`/`no_file_progress`/`text_loop`/`repetition:<sig>`.

## Decision

1. **Package + files**: new `internal/orchicon/session.go` (`Session` + identity), `internal/orchicon/loop.go` (agent loop), `internal/orchicon/transcript.go` (crash-safe JSONL), `internal/orchicon/bridge.go` (`Bridge` implementing `scheduler.AdapterBridge` + optional capabilities), and `internal/orchicon/loop_test.go` (mock provider). The engine is work-item-agnostic: it consumes only `scheduler.ExecutionManifest` fields (SystemPrompt, Goal, AcceptanceCriteria, ContextSources, ModelRef, Budgets, Stall*, ProjectDir/WorktreePath) — no work-item reads, no prompt re-rendering, so the same manifest shape serves Ask Orchicon.
2. **Session model**: ONE session per worker execution (session id == execution id). The identity block carries the worker's name/purpose + this task's description/AC; isolation by construction — no worker ever sees another worker's transcript. The model is bound once at session start from the worker's `orchicon/<provider>/<model>` ref (via `adapter.ParseModelRef` + `Registry.Get`); no per-turn model switch.
3. **Agent loop** (`loop.go`, in-process goroutine with `defer recover()` at the session boundary): OnStarted → assemble first user message = manifest Goal → turn loop bounded by `maxSteps` (an env-tunable constant, default e.g. 25; the budget JSON has no `max_steps` key today — the simulation path uses a hardcoded 3): build `TurnRequest` (System with the static prefix marked `Cache:true`, history, `registry.Defs()` tools), `StreamTurn`, drain events onto callbacks with the parity map (TextDelta→OnText chunked; ReasoningDelta→OnText reasoning wrapper, never replayed; complete ToolCall→execute after `Finish{StopToolUse}` + OnToolCall; write/write_artifact→OnArtifact; file-writing tools→OnWrittenFiles deduped; StreamError→surfaced error part + fail; Finish→usage record + turn dispatch) → append tool results as tool-role messages (consecutive tool messages merged, output capped at 128 KiB with truncation marker) → drain the injection queue between tool rounds → repeat until finish/guards. Terminal OnWrittenFiles (before) + OnResult (once).
4. **Tool execution**: the tool registry (tool-suite task) exposes `Defs() []orchicon.ToolDef` + `Execute(ctx, name, argsJSON) (resultJSON, error)`; the loop executes tool calls in parallel where independent (bounded worker pool, default 4), appends results to history, and a panicking tool is caught by the per-turn recover.
5. **Turn-loop guards**: max steps per execution (OnResult(false, "max_steps_exceeded")); no-progress detection via token growth (`Finish.Usage.TotalTokens` delta) + repeated tool signatures → `OnStall(ctx, execID, "stalled:no_progress"|"stalled:repetition:<sig>", fatal=true)`, surfaced to the platform stall/liveness layer (recovery trigger, existing handling). Cancellation: ctx cancel stops the loop gracefully (finish in-flight tool, no new provider call), marks the transcript `cancelled`, leaves the session resumable. Wall-clock deadline applies only to the provider/tool context, never the callback context (parity with the opencode adapter's documented writeback constraint).
6. **Crash-safe transcript** (`transcript.go`): append-only JSONL at `<project_dir>/.orchicon/sessions/<session_id>.jsonl`, one JSON object per line (`seq,type,ts,...`), **fsync per event** (`f.Sync()` after each append under a write mutex) — a kill -9 mid-run leaves a replayable transcript (torn final line tolerated). Resume = replay + continue (reopen the file in append mode, seek past the last durable line, rebuild history, continue the loop). The DB `execution_session_parts` stays the reconciliation-visible record (both written: DB best-effort, JSONL mandatory). Recovery (capture/summarize/resume) replays the JSONL. A panic inside the loop (tool execution, provider callback, transcript append) is recovered at the session boundary: the execution fails with the panic captured in its error output, the transcript is marked `failed`, and the control-plane process + sibling executions survive.
7. **Mid-run injection**: `Bridge.SendExecutionMessage` (MessageInjector) queues a user turn on the live session; the loop drains the queue between tool rounds and the reply streams back into the same session (same session id, same transcript file).
8. **Sequence continuation** (opt-in, default OFF): `ExecutionManifest.SequenceContinue bool` (scheduler sets it for consecutive same-worker chain tasks) — when set, the engine replays the prior session's JSONL and continues (retained context beats isolation); the engine verifies `priorSession.identity.WorkerID == session.identity.WorkerID` before replaying. Flag off (default) = fresh session with full isolation.
9. **Bridge + registration**: `Bridge` implements `AdapterBridge` (+ `MessageInjector`/`Aborter`/`LivenessReporter`/`ConfigurableBridge`); registered in `internal/server/server.go` as `dispatcher.Register("orchicon", nativeBridge)` — the concrete type appears only at construction (ADR-0003). The model-ref adapter segment `orchicon` already parses and worker validation already lists it as a known kind; no grammar change.
10. **Tests**: all against a `mockProvider` (scripted event streams) in `loop_test.go` — no live API in default tests (live smokes env-gated `ORCHICON_TEST_LIVE_<PROVIDER>=1` per provider-layer convention). Coverage: callback parity (text-only / tool-call rounds / parallel tool calls / mid-stream error), injection mid-loop, transcript crash-safety (kill -9 then resume), cancellation, guard behavior (max steps, no-progress), panic containment (panicking tool/provider/transcript-append), identity isolation + model bound once, sequence continuation on/off.

## Consequences

- The native adapter becomes a first-class `orchicon` bridge in the Dispatcher — executions whose worker model_ref is `orchicon/<provider>/<model>` run the in-process loop; opencode executions are unchanged. No scheduler/reconciler changes beyond the manifest fields (SequenceContinue, ContinueFromSessionID) and the one registration line.
- Crash-safe per-event JSONL transcripts make kill -9 mid-run replayable and sessions resumable in place; the DB parts remain the reconciliation-visible record (both written; a future consolidation is out of scope).
- Parity with the opencode surface (callbacks, chunking, stall reasons, completion semantics, tool-output capping, tool-role merge) means the reconciler/UI/recovery paths need no adaptation.
- Cost: the tool-registry contract (`Defs`/`Execute`) must land with or before the loop's tool tests (tool-suite task); per-event fsync adds latency (correctness-first; batching is a later optimization).
- Provider prefix caching across executions is preserved by keeping the static prompt prefix byte-identical and marking it as the cache breakpoint; per-session mutable state (goal/AC user message, tool results) lives after the breakpoint.
- Tests run entirely against the mock provider in CI; no API key or live provider required for the default suite.

## Alternatives considered

- **Extend the opencode adapter to run the loop** — rejected: the loop is native/provider-first and must not depend on the opencode serve transport; a separate bridge keeps the adapter kinds cleanly partitioned (ADR-0003).
- **DB-only transcript (batched flush, as today)** — rejected: not crash-safe per-event; a kill -9 can lose the trailing batch, which breaks the resume/recovery AC. The JSONL adds the crash-safe replay source while the DB stays the reconciliation record.
- **Per-turn model re-resolution** — rejected: the work item pins model binding at session start (no per-turn switch); the provider is captured in `Session` at construction.
- **Replay from the DB parts instead of the JSONL** — rejected: the JSONL is the higher-fidelity, per-event-durable source; the DB parts are coarser (kind+payload, batched) and would force a degraded resume.
- **Per-execution work-item reads / prompt re-render inside the engine** — rejected: the manifest already carries the assembled prompt; reading work items couples the engine to the scheduler's row model and would break the Ask Orchicon shared-manifest constraint.
